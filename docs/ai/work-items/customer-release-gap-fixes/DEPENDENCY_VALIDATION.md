# Dependency advisory validation

**Date:** 2026-10-05

**Scope:** Read-only review of the candidate's nine-package Python advisory summary. This is evidence triage, not an exploitability verdict, release/security approval, or a clean bill of health.

## Inventory reconciliation

`ADVISORY_INVENTORY.json` reports 108 scanner rows for nine installed packages. Exact package + primary-ID deduplication gives **70 distinct advisory identities** (bleach 3, cryptography 4, oauthlib 1, pdfkit 1, Pillow 13, PyJWT 14, pypdf 27, sqlparse 5, WeasyPrint 2). The other **38 rows repeat a package + primary ID** and fix version. Alias order differs; repeated Pillow rows also inconsistently omit BIT-prefixed aliases. Normalize on package + canonical identity and retain the union of aliases.

I fetched every exact GHSA identity through the primary [PyPA advisory database](https://github.com/pypa/advisory-database) for 65 PYSEC records and GitHub's [global advisory API](https://docs.github.com/en/rest/security-advisories/global-advisories) for the five GHSA/CVE-primary records. **All 70 identities matched an official record**: 65/65 PyPA YAML and 5/5 GitHub API responses were HTTP 200; package names matched; 0 records were not found, rate-limited, or failed; 70/70 have published/updated timestamps; none is marked withdrawn. The later-seeming 2026 PYSEC IDs were present in the official database at retrieval. All 70 identities also have a fetched GitHub advisory page containing the exact GHSA ID. Comparing those current GitHub affected ranges with the candidate gives **70/70 in range, 0 outside, and 0 unresolved**. This is package/version matching only, not proof of reachable exploitation. The GitHub page has 70/70 publication and review timestamps; the PyPA YAML/GitHub API records have 70/70 published and modified/updated timestamps. There were zero 404s, rate limits, other fetch errors, or withdrawn records.

There are **three inventory metadata discrepancies** to preserve for review: (1) one pypdf item uses `CVE-2026-57204` as its primary ID, but the official [GHSA-jm82-fx9c-mx94 record](https://github.com/advisories/GHSA-jm82-fx9c-mx94) says “No known CVE” and the API lists only that GHSA; the pypdf advisory itself is real, but its CVE label is uncorroborated. (2) twelve Pillow BIT-prefixed aliases in the inventory do not appear in the PyPA/GitHub source records; treat those alias labels as provider-specific and unverified here, not as extra vulnerabilities. (3) for PyJWT `PYSEC-2026-176`, the inventory says fixed in 2.13.0. The current [GitHub advisory page](https://github.com/advisories/GHSA-jq35-7prp-9v3f) reports affected `<2.13.0`, so candidate 2.12.1 is affected; the [PyPA YAML](https://github.com/pypa/advisory-database/blob/main/vulns/pyjwt/PYSEC-2026-176.yaml), modified 2026-06-02, instead reports fixed in 2.12.1 and excludes the candidate. This is a genuine source-range/fix mismatch (the GitHub page was published 2026-06-15), not a reason to dismiss the GHSA. For the other 13 unique PyJWT records, inventory fixes agree with the current GitHub ranges. The current GHSA pages corroborate the inventory fix versions for 69 records; the PyJWT identity above has a PyPA-vs-GitHub mismatch, while the inventory matches the current GitHub page. All original identifiers, source ranges, fix versions, aliases, timestamps and response hashes are preserved in the private raw evidence at `/home/mohamed/frappe-bench/release-tests/customer-release-gap-fixes/private/end-to-end-20261005/dependency-validation/normalized-public-metadata.json` and its source files.

## Use-path triage for the installed candidate

This is source tracing to prioritize review, not demonstration of an attacker-controlled route or impact:

- **bleach:** Frappe declares it, but the inspected sanitizer is `frappe/utils/html_utils.py`, which uses `nh3` and `bleach_allowlist`; no `bleach.linkify(..., parse_email=True)` call was found in Frappe/ERPNext/Construction. The GHSA-g75f condition specifically requires that opt-in path, so it is not shown reachable by this source search. This does not dispose of the separate sanitizer advisories or establish complete call-site absence across runtime plugins.
- **cryptography:** Frappe uses Fernet in password and backup utilities (`frappe/utils/password.py`, `frappe/utils/backups.py`). The verified 2026 advisories concern other cryptographic interfaces (including PKCS#7/X.509); assess those exact APIs and any transitive consumers before assigning app impact.
- **oauthlib / PyJWT:** Frappe uses oauthlib in OAuth request verification and server endpoints and imports `jwt` for OAuth token handling (`frappe/auth.py`, `frappe/oauth.py`, `frappe/utils/oauth.py`). Review the exact advisory preconditions against the configured grant and algorithm paths; presence is security-relevant, but not proof of exploitability.
- **pdfkit / pypdf:** Frappe's `frappe/utils/pdf.py` invokes `pdfkit.from_string` with `disable-javascript` and `disable-local-file-access` options and parses/merges resulting PDFs with pypdf. Construction also imports `PdfReader` for Variation Order PDF handling (`construction/construction/doctype/variation_order/variation_order.py`); tests construct PDFs too. Treat PDF bytes and render HTML as trust-boundary inputs and validate mitigations against the relevant exact records.
- **Pillow:** Frappe imports PIL in image utilities, File handling and identicon generation. Construction's search result only found PIL in a bilingual-report test, not its production Python modules. Review uploaded-image and any framework image paths against advisory-specific formats/operations.
- **sqlparse:** Frappe calls it in query construction/field checks, query formatting and recording (`frappe/model/db_query.py`, `frappe/utils/data.py`, `frappe/recorder.py`). The verified GHSA-f2ff record describes quadratic grouping of comment-only statements. Determine whether attacker-controlled SQL text can reach those parser call sites and whether a bounded query-size guard executes before parsing.
- **WeasyPrint:** Frappe reaches WeasyPrint through print-format paths (`frappe/utils/print_utils.py`, `frappe/utils/weasyprint.py`, `frappe/www/printview.py`). The verified GHSA-jf6q record is an SSRF advisory; review which HTML, CSS, URL fetchers, and print-format permissions can influence resource fetches.

## Candidate-compatible next steps

1. Prioritize the currently plausible PDF attack surface: pypdf parses user-provided Variation Order PDFs and Frappe print flows parse/merge generated documents; pdfkit renders print HTML and its advisory has no patched release; WeasyPrint is reachable through Frappe print paths and has SSRF findings. All 30 PDF-related unique identities (27 pypdf, one pdfkit, two WeasyPrint) match candidate versions in current GHSA ranges. Trace access controls and attacker influence over PDF bytes, print HTML/CSS, URL fetches, and effective wkhtmltopdf options. Add bounded input and SSRF/file-access controls only where the real call path requires them. `pypdf` is pinned exactly at 6.10.2 and relevant fixes begin later, so qualification needs an updated supported Frappe/ERPNext candidate or a separately reviewed effective mitigation.
2. Review the 14 PyJWT and four cryptography identities in current GitHub candidate ranges alongside Frappe's OAuth/JWT and crypto call paths, and the oauthlib PKCE condition against configured grants. Their reported fixes cross Frappe's constraints; qualify a coordinated framework/dependency release and test authentication, token algorithms, and certificate/PKCS#7 consumers rather than forcing an override.
3. Review the 13 Pillow and five sqlparse identities against actual upload formats, file/image handling, parser inputs, and pre-parse size bounds. Record each advisory-specific path as reachable, mitigated, not observed, or unresolved; the exact candidate-range match alone cannot settle exposure.
4. Correct the pypdf primary identifier to the corroborated GHSA (the official record says no known CVE); retain the 12 BIT aliases as unverified provider metadata until corroborated by their issuing provider. Resolve the PyJWT PYSEC/GHSA range conflict with the advisory maintainers; do not change the candidate version based on this evidence alone. Preserve the original 108-row scanner output and this 70-record source manifest for traceability.
5. Keep current framework constraints intact during triage. Any dependency change belongs in a separately resolved and tested Frappe + ERPNext candidate. Rebuild and rescan that candidate, then rerun affected PDF, image, query, OAuth, security and business checks. This evidence does not establish reproducibility or security readiness.
