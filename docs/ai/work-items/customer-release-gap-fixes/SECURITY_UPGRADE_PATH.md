# Version-16 security dependency upgrade path

**Reviewed:** 2026-10-05

**Purpose:** Compare official Frappe/ERPNext version-16 release metadata with the 70 already reconciled GitHub advisory identities. This is a candidate-selection note, not an exploitability assessment, security approval, or proof that a candidate environment is resolved or tested.

## Official candidate examined

As of this review, the newest official pair evidenced by GitHub releases is [Frappe v16.36.1](https://github.com/frappe/frappe/releases/tag/v16.36.1), release commit `97a5dd93ca5883bcc9c4ef9834120c5cba397b67`, together with [ERPNext v16.37.0](https://github.com/frappe/erpnext/releases/tag/v16.37.0), release commit `af63cde4941570ec7b9e12422c68302762cfcf91`. Their release pages date both releases 2026-09-30. Frappe's tagged [pyproject.toml](https://github.com/frappe/frappe/blob/v16.36.1/pyproject.toml) and current [version-16 branch pyproject.toml](https://github.com/frappe/frappe/blob/version-16/pyproject.toml) report the same nine-package constraints listed below. ERPNext's [v16.37.0 pyproject.toml](https://github.com/frappe/erpnext/blob/v16.37.0/pyproject.toml) requires Frappe `>=16.21.0,<17.0.0`, which the paired Frappe release satisfies; ERPNext has no direct requirement for the nine packages. Frappe v16 declares Python `>=3.14,<3.15`. The upstream support plan lists version 16 on the `version-16` branch with planned support through end of 2029 ([supported versions](https://github.com/frappe/erpnext/wiki/Supported-Versions)).

This identifies a plausible maintained base for an isolated candidate build. It does **not** assert that the Construction app or customer workload is compatible with it, or that framework release metadata is a reproducible lockfile.

## Constraint versus advisory-fix matrix

“Allowed” below means the Frappe release constraint admits the cited fix version; it does not mean the release archive or a resolved local environment was installed and inspected. Counts refer to the prior 70 unique advisory identities and the current GitHub affected/fixed ranges reconciled there.

The constraints establish that current version-16 upstream has addressed some original findings (notably cryptography and Pillow) and adopted the sqlparse 0.6 line, but the selected release does **not** remove the whole advisory set. It leaves framework-bounded OAuth/JWT and PDF issues, and it gives no direct resolved-version guarantee for Bleach. A new candidate must be built and audited before these metadata allowances count as candidate evidence.

## Recommended isolated work sequence

1. **Create a separate Bench-managed candidate** pinned to the exact Frappe/ERPNext commits above, with the Construction app at an explicitly reviewed commit. Keep the current environment unchanged. Resolve and preserve the complete Python dependency graph (including Bleach, pyOpenSSL, sql-metadata, and SQL parser versions), interpreter and platform artifacts; reject solver conflicts rather than adding silent direct overrides.
2. **Close the PDF work package first.** The source trace already identified user-provided Variation Order PDFs flowing to pypdf, Frappe PDF parse/merge, pdfkit print HTML, and WeasyPrint print paths. The upstream pair's pypdf 6.15.0 is still below 11 reviewed fixes, WeasyPrint 68.0 is below the SSRF fix, and pdfkit has no reported patched version. Trace actual authorization and attacker influence; verify local-file/URL-fetch protections, redirect/SSRF boundaries, temp-file/path handling, and bounded CPU/memory/page/file sizes with negative tests. Select a supported renderer/framework upgrade or a documented compensating control per demonstrated route.
3. **Qualify authentication and crypto.** Test Frappe's OAuth grants, JWT algorithms/key/JWK fetch behavior, redirects and refresh/error cases against the exact PyJWT advisories. The current Frappe range leaves 9 later PyJWT findings and oauthlib's 4.0 fix outside its 3.3.x cap. The cryptography 50/pyOpenSSL 26.4 combination is metadata-compatible and clears the four listed crypto ranges, but still needs regression coverage of Frappe crypto consumers and certificate/PKCS#7 handling.
4. **Qualify uploads and parsers.** Test accepted formats and limits through the actual upload/preview paths against Pillow's fixed 12.3 range, then exercise SQL parsing/query/report paths with adversarially large/comment-heavy input under the upstream sqlparse 0.6 / sql-metadata 3 pairing. Check for dependency behavior changes in Construction and its tests.
5. **Re-run the full candidate evidence suite**: resolved dependency/advisory scan, app and framework tests, financial/report/upload/OAuth/PDF regressions, supported Python/platform build, migration/restore and operational checks. Record exact candidate IDs, lock/hash artifacts, logs, failures and residual advisories. Security review and release approval remain separate decisions.

## Evidence limits

Source basis is official public release/branch metadata and the previously reconciled local advisory manifest. Public refs were read only; no private source, customer data, or site data was sent to external services. This review did not fetch/install packages, solve a new environment, inspect PDF attack payloads, test mitigations, or execute site commands. The current upstream `version-16` ref can advance after this review; repeat the comparison against the exact commits selected for any candidate build. This note does not establish exploitability, mitigation effectiveness, support compatibility for Construction, or release/security readiness.
