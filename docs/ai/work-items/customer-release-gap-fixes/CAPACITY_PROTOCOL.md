# Bounded capacity probe protocol

**Status:** private measurement protocol only; no workload or customer capacity is approved by this document. The owner-facing engineering profile below is a test profile, not an offered or sold limit.

## Scope and guardrails

Use only the newly provisioned, disposable site named `release-capacity.localhost` in `/home/mohamed/frappe-bench/release-tests/customer-release-gap-fixes`. The probe itself verifies the exact site name and resolved site directory before fixture or measurement work. It does not provision sites, touch any other site, save raw site configuration, or print configuration/secrets. Its guarded driver commits only synthetic fixture data after integrity audits pass. Retained fixtures and generated XLSX files remain on this disposable site; remove the site only through its separately approved private-bench lifecycle. Do not run the script against `v16.localhost`, `release-gaps.localhost`, `release-install.localhost`, a customer site, or another bench.

The bounded engineering test profile is **10 Projects × 2,000 BOQ Items per Project (20,000 rows), with at most 5 simultaneous read requests**. It is synthetic read-fixture data only. Bulk seeding bypasses native item/structure writes and does not measure customer authoring, import commit, or write capacity. API/export/XLSX/concurrency results are taken on one representative 2,000-item BOQ; the other nine headers establish the full ten-project fixture and aggregate audit, not nine more timing samples. This is a candidate measurement point only. Do not interpret success, failure, or a timing threshold as an owner-approved capacity promise. There is no invented SLA threshold in this protocol. The owner must select a supported workload and acceptable response/memory/worker behavior before any customer capacity claim.

## Probe behavior

The private helper is `capacity_probe.py` beside this protocol's private fixture artifacts in the private bench. Load it from a Frappe console after the parent operator has created and verified the target site. The helper provides:

- `seed_profile(run_id, projects, items_per_project, fixture_mode)` with hard caps of 10 Projects and 2,000 items per Project.
- `measure_header(header_name, repetitions)` for native BOQ structure summary, revised BOQ report payload, and full BOQ export source payload construction. It records per-operation p50/p95 latency, serialized response bytes, before/after process RSS, and cumulative process peak RSS.
- `measure_xlsx_export_once(header_name)` to run the real private `BOQExportService.export_to_excel` operation once and measure elapsed time, actual XLSX bytes, and process RSS. It creates one private File attached to the synthetic BOQ and deliberately retains it; one call avoids filename collisions and artifact accumulation.
- `measure_admitted_cost_workbook_boundary(run_id)` to generate an ordinary, valid workbook with exactly 2,000 imported rows and measure the production cost-database parser's dry-run path. It uses the existing 25 MiB file ceiling, creates no business records, and does not create a hostile or unusually compressed archive.
- `measure_simultaneous_readers(header_name, readers, rounds)` for up to five independent Frappe connections running the revised report payload concurrently as Administrator. It reports request latency percentiles, wall time, completion count, and process peak RSS. Every response is checked for the expected row count; the fixture audit checks totals before timing. This does not qualify the owner-unresolved role/scope matrix or distinct real customer sessions.

Seed always uses native Project and BOQ Header document lifecycle. Calibration uses `fixture_mode="native"`: each native BOQ Structure leaf creates its unique BOQ Item through normal lifecycle. For the large read profile, `fixture_mode="bulk"` inserts one unique synthetic leaf Structure per item and its matching BOQ Item through `frappe.db.bulk_insert`. This bypasses both document controllers, the per-leaf WBS generator and ordinary per-item validation solely to keep generation bounded; it is not evidence of document creation, import, or authoring throughput. The synthetic forest assigns unique WBS codes and disjoint contiguous `lft/rgt` pairs. Before measurement, both modes check one structure per item, distinct WBS codes, contiguous valid NestedSet intervals, contract value (25 per row), estimated/direct cost (20 per row), and persisted header totals after native aggregate recalculation. The actual native rollup audit must return the expected header and per-structure fields with empty `mismatched_fields` lists; a missing or unexpected response shape fails closed. A failed audit blocks measurement. Permission checks are bypassed only for private fixture creation (`ignore_permissions=True`). Rollups are deferred during seeding then refreshed once per header after restoring normal lifecycle flags. Synthetic rows must not be loaded into any other site.

The revised-report operation and export source payload invoke the application query/services rather than inventing synthetic response models. The report-payload measurements include response serialization byte counts. `measure_xlsx_export_once` separately measures actual XLSX generation, writing and private File registration. The cost workbook probe exercises the admitted 2,000 imported-row boundary in validation-only mode through the production parser service; it does not qualify multipart transport or database writes during a real import commit. Do not test safety limits by constructing huge/malicious archives.

## Calibration then profile

Run `capacity_driver.py calibration` with a 15-minute outer timeout. It creates a Company through native Company lifecycle and sets private Global Defaults to EGP/Egypt if none exists, then seeds `calib1` with one project × 25 items. It commits only after count, amount, NestedSet, and native header/structure rollup audits pass. It measures the three native API/payload paths (3 repetitions), one real XLSX export, two independent readers × three rounds, and a dry-run cost workbook at the supported 2,000-imported-row boundary. Calibration helps catch environment, schema, fixture, and response-shape errors; it does not qualify production capacity.

After calibration passes, run `capacity_driver.py profile` with a 30-minute outer timeout. It seeds the exact 10×2,000 bulk profile, validates each header before committing, then measures API/payload paths (3 repetitions), one real XLSX export, and five simultaneous readers × three rounds on the first 2,000-item BOQ. Run the independent 2,000-import-row parser boundary as `capacity_driver.py cost-boundary` with a 15-minute outer timeout. MariaDB statement time is capped at 120 seconds; concurrency barrier wait is capped at 60 seconds. Preserve timeout/failure output. This probe neither flushes nor controls Redis or other caches.

Illustrative bounded invocation from the private Bench `sites` directory (preserve both streams in private logs):

```python

  /home/mohamed/frappe-bench/release-tests/customer-release-gap-fixes/rebuilt-env/bin/python \

  2>&1 | tee /home/mohamed/frappe-bench/release-tests/customer-release-gap-fixes/logs/capacity-calibration-20261005.log
```

The guarded runner accepts only rebuilt-env Python, the exact candidate worktree on `PYTHONPATH`, the private Bench `sites` cwd, and the exact site guard. It enforces a 120-second MariaDB statement limit and must be launched with outer timeouts (calibration 15 minutes, profile 30 minutes, workbook boundary 15 minutes). A timeout means preserve the partial log/result and stop; do not shrink or silently repeat the workload. The runner commits calibration/profile fixture data only after audits pass and records the transaction decision. Raw JSON is written under `/home/mohamed/frappe-bench/release-tests/customer-release-gap-fixes/private/end-to-end-20261005/capacity-results-20261005.json`; XLSX/File output remains on the private site. It never serializes configuration or prints credentials.
