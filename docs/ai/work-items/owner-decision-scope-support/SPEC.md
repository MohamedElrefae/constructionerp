## 0. Problem Statement

A workflow paused with `gate = {"scope": "DECISION", ...}` **cannot be resumed through any
sanctioned mechanism.**

`orchestrator/schemas/v1/approval-token.json` declares five `oneOf` branches with scopes
`PLAN`, `PLAN` (v2), `COMMIT`, `DRY_RUN`, `IMPORT`. There is no `DECISION` branch.
`Engine.approve()` (`engine.py:2093-2098`) requires `token["scope"] == view["gate"]["scope"]`,
so a `DECISION` token is required — and is rejected by the schema.

`_owner_gate` (`engine.py:626-628`) refuses to resume without a validated event:

```python
# Resumption carries no authorization. Only validated SQLite events can change state.
if not self.store.events(v["cursor"]):
    raise WorkflowError("No recorded owner decision to resume")
```

Consequence: the only available transition is a direct `workflow_events` insertion plus a
manual checkpoint-gate clear — the pattern recorded at §2.3 of
`workflow-reconciliation-and-manual-intervention-audit.md`, which bypasses validation and
produced Finding SCP-006.

---

## 1. Design Principles

1. **A decision is content-bound, never a blank cheque.** A `DECISION` token is valid only
   for the exact candidate, plan, scope, repository, branch, and finding set it names.
2. **A decision is not a commit.** `DECISION` clears an owner-decision gate only. It must
   never imply release authority; `COMMIT` remains a separate, independently gated token.
3. **Replay resistance.** One token per gate (`token_id` uniqueness, already enforced by
   `approve()` at `engine.py:2087-2091`), plus content binding so a token minted for one
   candidate cannot be replayed against another.
4. **Fail closed.** Any missing or mismatched binding raises. No partial acceptance.
5. **Separation of duties.** This change lands in its own candidate and its own cycle. It
   must never be folded into a feature candidate that it governs.

### 2.1 Field rationale

| Field | Purpose |
|---|---|
| `disposition` | Constrains what the decision *does*. Prevents an unbounded "acknowledge" token. `WAIVED` must be recorded distinctly from `RATIFIED` so waivers remain greppable. |
| `decision_hash` | SHA-256 over the canonical UTF-8 bytes of the decision markdown (rationale included). Single field, per owner ruling Q3 — replaces the earlier `rationale_sha256` to eliminate divergent-document risk. |
| `candidate_id` | Replay guard — this decision applies to this candidate only. |
| `plan_revision_hash` / `scope_hash` | Same binding semantics as the `PLAN` v2 branch (`engine.py:2103-2120`). |
| `resolved_finding_digests` | **Replaces the earlier `finding_ids`** — see §2.3. Each entry is a `snapshot.reproduction_digest` from a blocking finding on this gate. Ledger-verifiable and stable. |
| `expected_parent_sha` | Base commit the decision is bound to. Prevents a decision surviving a rebase or history rewrite. Mirrors the `COMMIT` branch. |
| `supersedes_decision_hash` | Optional. Chains a replacement decision, preserving history rather than overwriting. |

### 2.3 Why `finding_ids` was replaced by `resolved_finding_digests`

**Correction (revision 4).** The first draft of this section overstated the defect. Measured
against the live ledger:

| Location | `finding_id` |
|---|---|
| Raw event `workflow_events` seq 45 (`result-job-dda5c2c7ba98b37abe491473`) | `null` for all three findings |
| Normalized checkpoint `view["findings"]` | `SCP-006`, `SCP-007`, `SCP-008` — allocated by `routing.findings()` |

`routing.findings()` (`routing.py:88-116`) assigns `"SCP-" + str(next_finding).zfill(3)`
whenever an incoming finding carries `finding_id is None`. So the `SCP-###` labels **do**
exist in workflow state. The earlier claim that they "appear nowhere in the ledger" was
wrong: it holds only for the raw event payload, not for the normalized state.

The digests map exactly as tabulated, confirming the pairing is correct:

| `finding_id` (normalized) | `snapshot.reproduction_digest` |
|---|---|
| `SCP-006` | `2060223e47de5207bcb353e90c12510fe43b055702ffd07c587ca335d884b9ca` |
| `SCP-007` | `482c9a4ca103485e10137d4f0397e977cae98b31b46c15e40d5e90490f1829c6` |
| `SCP-008` | `930e1a60f6f9bea4cf3032322764b592521cf59c4f7e09fca69d40386b8580fe` |

**The design decision still stands, on corrected grounds.** `resolved_finding_digests` is
retained because `reproduction_digest` is *content-addressed* while `SCP-###` is
*counter-allocated*:

- `SCP-###` depends on `state["next_finding"]` (currently `9`). The same underlying finding
  would receive a different label under a different arrival order, so a decision bound to
  `SCP-006` could silently stop referring to the same claim after a re-run.
- `reproduction_digest` is derived from the finding's own content and is stable under
  renumbering, re-verification, and replay.
- `routing.finding_identity()` (`routing.py:83-87`) *already* uses `reproduction_digest` as
  the canonical identity for deduplication. The decision binding therefore matches the
  engine's own notion of "same finding" rather than introducing a parallel one.

Both fields are consequently recorded: `resolved_finding_digests` is authoritative, and
resolved findings retain their `SCP-###` label in the workflow state for human reference.

### 2.4 Non-goals

`DECISION` deliberately has **no** `job_id`, no `expected_parent_sha`, no `expected_tree_oid`,
and no `manifest_hash`. It confers no authority over commits, exports, or ERP operations.

## 3. Item 2 — `Engine.approve()` and `routing.apply_event()` Handling

> **Correction (implementation).** Scope validation belongs in `Engine.approve()`, but the
> **gate-clearing state transition belongs in `routing.apply_event()`** (`routing.py:498+`),
> where every other scope's post-grant transition is defined. `routing.py` was absent from
> this spec's file list and is now a required change.

Insert a `DECISION` branch alongside the existing scope branches, after the `IMPORT` branch
and before the `else` at `engine.py:2231`.

```python
elif token["scope"] == "DECISION":
    # Decision authority is bound to exact content; fail closed on any drift.
    self._recheck_candidate(view["candidate"])
    required = dict(
        candidate_id=view["candidate"]["candidate_id"],
        plan_revision_hash=view["plan_revision_hash"],
        scope_hash=view["scope_hash"],
        repository_id=str(self.root),
        branch=self.config["branch"],
        expected_parent_sha=self.config["base_commit"],
    )
    if any(token.get(k) != value for k, value in required.items()):
        raise WorkflowError("DECISION binding mismatch")

    if token["disposition"] not in ("RATIFIED", "WAIVED", "REJECTED", "SUPERSEDED"):
        raise WorkflowError("DECISION disposition is not permitted")

    # Every finding the owner claims to resolve must actually be open on this gate,
    # identified by its ledger reproduction_digest (see §2.3 — finding_id is null).
    open_digests = self._open_finding_digests(view)
    ungrounded = sorted(set(token["resolved_finding_digests"]) - open_digests)
    if ungrounded:
        raise WorkflowError(f"DECISION references findings not open on this gate: {ungrounded}")

    if token["disposition"] == "SUPERSEDED":
        prior = token.get("supersedes_decision_hash")
        if not prior or not is_hex64(prior):
            raise WorkflowError("SUPERSEDED disposition requires supersedes_decision_hash")
        if prior == token["decision_hash"]:
            raise WorkflowError("SUPERSEDED decision must differ from the decision it supersedes")
```

### 3.4 Partial resolution — DEFERRED (not implemented)

**Status: deferred, with rationale.** The original §3.4 asked a `DECISION` token naming
fewer digests than the gate carries to clear only those and re-pause for the remainder.

Implementation found this is **not safely achievable with the primitives the engine has**:

- Findings are not resolved by grants. `routing.apply_event` recomputes
  `state["findings"]` from the **next result event** (`routing.py:155-167`); there is no
  per-finding resolution primitive to call.
- An initial implementation called `pause()` on a `view` and mutated state directly from
  `approve()`. `routing.pause()` expects a `state` dict with `revision`/`status`/
  `next_roles`, and mutating it outside `apply_event` bypasses the cursor/revision
  bookkeeping that `apply_event` performs at its tail. That code was **removed rather than
  shipped**.

A `DECISION` grant therefore authorizes **progression**; findings remain in state and are
recomputed by the next authoritative result. Disposition routing is implemented and tested:

| `disposition` | Resume target |
|---|---|
| `RATIFIED` / `WAIVED` | `prior.status` / `prior.next_roles` (where the pause occurred) |
| `REJECTED` | `NEEDS_REVISION`, `next_roles=["architect"]` |

Every claimed digest must be open on the gate (`_open_finding_digests`), so a token cannot
clear a finding it does not name. Per-finding partial clearing requires a new engine
primitive and is **deferred to a follow-up work item** rather than approximated unsafely.

#### Original §3.4 text (superseded, retained for audit)

> A `DECISION` token may name **fewer** digests than the gate carries open findings. When it
> does, the engine must clear the gate only for the named digests and **immediately re-pause**
> with a fresh `DECISION` gate for the remainder, rather than treating the whole gate as
> resolved.

A `DECISION` token may name **fewer** digests than the gate carries open findings. When it
does, the engine must clear the gate only for the named digests and **immediately re-pause**
with a fresh `DECISION` gate for the remainder, rather than treating the whole gate as
resolved.

This matters concretely for `decision-44`: if the owner ratifies only SCP-006
(`2060223e…`), the gate must re-pause for `482c9a4c…` and `930e1a60…`. Silently clearing all
three because one digest was named would be exactly the over-broad clearing that §3's
ungrounded-claim check exists to prevent.
