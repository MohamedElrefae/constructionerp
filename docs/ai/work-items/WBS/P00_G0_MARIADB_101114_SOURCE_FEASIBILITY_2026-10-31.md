Status: source-and-document analysis; **BLOCKED, not acceptance-ready, not an execution grant**. Scope: selected public upstream reference source and public Ubuntu package listing. ## Verdict

The public upstream 10.11.14 source shows a relationship between SQL transaction state and InnoDB state and shows that the `INNODB_TRX` indicator is read from cached InnoDB state. The selected source does **not** establish that this indicator reliably proves active transaction-level enforcement on the exact Ubuntu package, or that a live observation corresponds to the same uninterrupted transaction. The exact Ubuntu patch set, build and source-to-binary chain were not reviewed or verified. Feasibility remains unresolved, not proven impossible. Metadata, session variables, status flags, a successful query and similar signals, alone or combined, are not a qualified enforcement proof. No candidate can pass the gate today.

## Reference findings and provenance

1. Upstream tag `mariadb-10.11.14` [SQL transaction source](https://github.com/MariaDB/server/blob/mariadb-10.11.14/sql/transaction.cc#L146-L196) sets a thread transaction read-only flag for explicit READ ONLY and sets a read-only server-status flag when it begins a transaction. This is a source-path observation, not a proof that all enforcement paths are covered or that the flag proves enforcement in an actual running session.
2. The [InnoDB handler](https://github.com/MariaDB/server/blob/mariadb-10.11.14/storage/innobase/handler/ha_innodb.cc#L1581-L1589) exposes a helper that reads the thread read-only property. Separately, [transaction cache code](https://github.com/MariaDB/server/blob/mariadb-10.11.14/storage/innobase/trx/trx0i_s.cc#L435-L457) copies `trx->read_only` into the cached `trx_is_read_only` field; [the schema reader](https://github.com/MariaDB/server/blob/mariadb-10.11.14/storage/innobase/handler/i_s.cc#L459-L465) outputs that cached field. This is a partial source trace only: the initialization and transition paths connecting the helper to `trx->read_only`, and all SQL enforcement and storage-engine paths, are not comprehensively traced. The mere existence of both flags does not establish equivalence.
3. The [reference schema reader](https://github.com/MariaDB/server/blob/mariadb-10.11.14/storage/innobase/handler/i_s.cc#L159-L184) calls a global `PROCESS_ACL` access check before filling `INNODB_TRX`; the same code can emit a cache-truncation warning. [Cache construction](https://github.com/MariaDB/server/blob/mariadb-10.11.14/storage/innobase/trx/trx0i_s.cc#L978-L1013) skips not-started transactions and can reuse a cache instead of refreshing it. Thus, as an inference, a row may be unavailable or stale; empty output and a matching row cannot independently prove complete current visibility or continuity. Exact resulting client behavior and warning delivery need separate verification. A principal without the required privilege cannot rely on this reference path; no PROCESS grant, privilege inspection or escalation is authorized.
4. Ubuntu's [package listing](https://packages.ubuntu.com/da/noble-updates/mariadb-server) identifies source package `mariadb` version `1:10.11.14-0ubuntu0.24.04.1` and lists an upstream archive, signature, Debian patch archive and source descriptor. The package epoch `1:` is package-version syntax; do not append it to the accepted server version string. The listing is not proof the reported version string, source, patches, package, executable or runtime match each other. The selected upstream tag has not been cryptographically authenticated or compared to the Ubuntu archive or patches, nor has reproducibility or a running binary been established.

## Correlation and visibility: requirements, not an available recipe

A candidate must bind: trusted server instance and boot/instance epoch; authenticated connection and intended principal; a server-origin transaction generation with demonstrated uniqueness/lifetime; and an unbroken interval from verification through every predeclared identity query. The verifier must prevent or detect transaction end/replacement, implicit commit, reconnect, pool reassignment, concurrent use and identifier reuse. Freshness must be independently justified; client-generated tokens, transaction ID, connection ID, timestamp, or a pair of snapshots alone are insufficient. An observer outside the session additionally needs authenticated binding between its observation and the executing transaction. No primitive satisfying all of this has been established.

The intended principal is not selected or authorized. Its minimum needed visibility is the exact, version-qualified non-secret server/transaction state and correlation evidence required by the chosen verifier, plus bounded error and cleanup states; it must not collect statement text, credentials, user identities, or unrelated records. Completeness evidence must establish access-check semantics, row coverage, freshness, non-truncation, relevant engine/statement coverage and correct transaction identity using an independent trust chain and negative controls. A successful query or zero rows proves none of these. The source shows PROCESS is checked for this upstream `INNODB_TRX` path; it does not prove that the actual target has the same code or that this privilege is acceptable. Do not retry with broader privilege.

## Attestation and non-mutating observation boundary

A hypothetical independent attester must have a separately authenticated trust anchor; build/instance/transaction binding; replay resistance and freshness; separation from the verifier and evidence producer; a reviewed account of server implementation and patch effects; independent measurement of its own coverage; and independently protected evidence. An audit plugin, proxy, restricted principal or global read-only setting is a distinct candidate, not proof of transaction-level enforcement. No candidate, observer, trust anchor or target binding is qualified. A disposable environment's paired write-rejection and read-write positive controls could assess a design only after separate authorization; they do not by themselves prove target enforcement. No target write challenge is permitted.

The **complete allowable observation set is unresolved**, because no candidate is qualified. A future closed allowlist must specify exact principal, operation, inputs, state read, output domain and side effects for: server/build provenance; connection and transaction identity/continuity; active enforcement; visibility and freshness; pre-gate ordering; verifier and observer integrity; failure, rollback and connection closure; and redacted evidence. Reject unlisted operations. No target write or temporary-object mutation, SQL/script body, credential, user/document identifier, unbounded error text, side-effecting function, sequence advance, advisory lock or file export is allowed. Session changes needed to start a transaction must be separately classified and justified; no presumption that any SELECT, instrumentation, logging or transaction statement is side-effect free. A proposal that cannot bound its outputs or demonstrate non-mutation stays BLOCKED.
