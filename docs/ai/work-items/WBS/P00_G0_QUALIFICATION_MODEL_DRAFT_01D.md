## 1. Model and outcome rules

A **campaign** is a proposed collection of mandatory variants under one reviewed catalog. A **case** groups related variants. A **variant** has one ID and defined expected outcome. An **attempt** is one separately authorized run of exactly one variant in one separately bound disposable generation. A campaign may contain multiple attempts only under separately current scoped authorizations. A stopped attempt never resumes; cleanup remains possible. Retrying any incomplete attempt requires fresh authorization, never broader privileges. Attempts are not target checks and no lab mutation may be used on target.

Variant result: `PASS`, `FAIL`, `UNKNOWN`, `NOT_RUN`. PASS requires all expected conditions, qualified independent evidence and confirmed cleanup/sealing; an expected safe denial in a negative variant may be PASS for that variant only. FAIL requires independently established contrary observation. UNKNOWN means unavailable, ambiguous, unqualified, unsafe, or contradictory evidence; NOT_RUN means no authorized execution. A nonterminal observation does not become PASS. For each mandatory variant exactly one independently reconciled terminal outcome is needed; duplicates, absent, extra, conflicting or retracted records force campaign INCOMPLETE until resolved by a separately reviewed correction. Case PASS requires all its mandatory variants PASS; case FAIL requires at least one independently evidenced FAIL; otherwise case UNKNOWN if any variant UNKNOWN or missing, or NOT_RUN if none ran. Campaign classification: `LAB_CASES_COMPLETE` only if all mandatory variants PASS, all required independent attestations and cleanup/seals confirmed, and reconciliation is independently accepted; `FAILED` if a confirmed FAIL and no uncertainty about necessary evidence/cleanup; otherwise `INCOMPLETE`. An expected negative stop does not itself fail a campaign. Missing/unsafe/suppressed evidence never becomes PASS. Lab completion is a bounded lab observation, not target qualification, G0 closure or activation.

## 3. MariaDB version classification

Comparison is byte-exact ASCII with no trimming, case folding or normalization. Recognized reference is only `10.11.14-MariaDB-0ubuntu0.24.04.1`. Exact reference yields `MATCH_REFERENCE` subject to all other gates; it does not prove runtime binding or independent baseline. A well-formed different numeric major/minor/patch yields `NUMERIC_MISMATCH` and stop. If numeric triple is exactly `10.11.14` but suffix differs, is absent, contains case/whitespace changes, extra text or is unrecognized, output `UNKNOWN` and stop. Malformed/non-ASCII, extra numeric segments, leading/trailing whitespace or ambiguous parsing output `UNKNOWN` and stop; no raw unexpected bytes, length or hash. This conservatively classifies a bare version as UNKNOWN; it does not redefine the accepted baseline. The exact grammar and parser require independent review and qualification. Results are point observations only.

## 4. Record lifecycle and aggregation

Proposed record types, each immutable after finalization: (1) prebound attempt/variant outcome, (2) independent observer attestation, (3) independently verified cleanup/seal attestation, (4) campaign reconciliation, and (5) separate witness-qualification and custody-acceptance attestations. Record 1 is finalized only after cleanup and sealing outcomes are known, or records UNKNOWN if they cannot be safely established; it cannot self-attest independent evidence. If a terminal record cannot safely be emitted, no fabricated record is created: campaign remains INCOMPLETE and a separately approved safe escalation channel is used only if it can be proved non-leaking. A campaign summary must be independently reconciled against the fixed catalog and separately authenticated; producer or custodian cannot self-accept custody evidence. Append-only correction records link by approved non-sensitive reference to superseded versions; originals are not overwritten and ambiguity blocks acceptance. Authority, trust root, role constraints, reference format, exact cardinality, redaction and integrity implementation are still UNQUALIFIED; the model is not a working evidence system.

All records and manifest require fixed reviewed schema, controlled enums, fixed cardinality/order and identical redaction boundary; no free text or raw SQL/error/account/config/fixture/credential/unexpected-value/canary. No hashes of secrets, unexpected values or low-entropy confidential values. Suppress any field or entire record if slot IDs, counts, timing, filename, reference or ordering can expose a suppressed value; absent/suppressed record makes campaign INCOMPLETE. Protected hashes of reviewed non-secret artifacts and manifest reference require separate approval, not assumed safe merely because hashed. Separate qualification and acceptance attestations need authenticated, independent authority and role binding; separate files or AI review do not establish independence. User identity collection is prohibited; target identity comparisons are limited to fixed approved target fields, in memory under a future authorization, with match/unknown output only. Exact source provenance, scope and safe query projections remain undefined.
